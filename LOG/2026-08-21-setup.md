# f3f5668 — /setup migration: format 3 → 4, build blocks written onto all 23 cleared build items, and an uncleared red flag filed on the MCP server's auth model

The previous session stopped on the format 3 → 4 drift rather than planning against documents in a shape this plugin version no longer reads correctly. This session ran that migration. Only one epoch section applied — epoch 4, which requires every item cleared to run to carry a build block, since a run reads a generated view assembled from those blocks and never reads QUEUE.md. Without one, a cleared item reaches the run with no instructions and halts it as underspecified. Everything else the checklist covers was already done by the 2026-08-19 migration: the two-section queue, the mailbox, the retired REGISTRY.md, the `.throughliner-*` marker names.

The real decision was what to do with the seventeen numbered items ([0006-side-scrolling-date-picker] through [0022-help-thanks-report-a-bug-content]) whose queue text is a one-line summary plus a pointer to an archived batch spec. The checklist's default is that an item not stating what changes inside its files never passed the keep check, and should go below the readiness line for a planning session to process. Applying that literally would have emptied the cleared region from twenty-three build items down to six. The alternative offered was to lift the blocks from the archived specs, which do carry real Changes lists. Both were put to the user with the second recommended; the user chose it ("as you recommend"), so the recommendation and its reasoning are Claude's and the decision to take it is theirs.

What made the lift legitimate rather than an invention of instructions: the archived specs are recorded material this project wrote, not a guess at what the items meant. Where a spec named behaviour but no file, the block names the files from the current source tree — `EditTaskScreen.kt` for the date strip, `SlotPage.kt` and `LaterPage.kt` for the drag work, `SlotDeriver.kt` for the day boundary — and where the code does not exist yet (the tier, sync, MCP and onboarding items) the block describes the scope and cites the spec rather than naming files that would be fiction. Every block also cites its archived spec, so the fuller text stays one hop away.

Three blocks carry a `Refused:` line, which is the one thing that travels out of an item's decision history into its block: Android's edge-swipe-to-open convention on [disable-drawer-swipe-open], an in-app recently-cut buffer on [0011-cut-and-paste-os-clipboard], and the separate-completed-history-page framing on [nav-left-spine-spec-edit]. A build that cannot see why an option was rejected proposes it again and stops to ask, which is the cost that line exists to avoid.

Two blocks fold in work held elsewhere rather than leaving it to be rediscovered: [0012-settings-day-begins-at]'s block absorbs [schedule-day-boundary-tick]'s recompute-on-boundary requirement, which its own prose already said should ride that wiring, and [0014-json-export-and-import]'s block names the two questions [bridge-asks-from-method-project] asks of it — whether an additive import is possible, and whether completions can be read out of an export — so they are settled with that item's design rather than after it.
