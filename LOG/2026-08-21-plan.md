This session ran across 2026-08-20 and 2026-08-21.

Three things drove it. The first was a correction: the standing capture about `CLAUDE.md`'s stale workflow vocabulary claimed the wrong cause. It said the file carried the user's own wording and so could not be reconciled against the template without clobbering it. Reading the file showed the whole stale passage sitting *inside* the `PLUGIN-MANAGED` markers, which the plugin owns and refreshes on /setup and reinstall — the user's Project rules sit outside them, untouched. The installed plugin's template was read and found current and correct, so there was nothing to negotiate and the item became a straight swap. The item was itself going to be a planning edit until the planning scope-lock refused `CLAUDE.md`, which is why it is filed as a build rather than done in the session that found it. The second was the spine's left half. [nav-completed-history] bundles four sub-features and named three open questions blocking it. Two were settled with the user. Search and completed-history are **one unified page** rather than two surfaces: the user's call, on the ground that someone hunting a task usually does not know or care whether they already finished it, and two search boxes means guessing which to open. Weighed against it and accepted: the page now does two jobs, and [search-feature]'s read-only-results rule sits awkwardly beside a completed list the user is meant to tap into and uncomplete — the day-card layer resolves that, since editing happens only from a card. The share-a-day format is **PNG and Markdown, both offered**; the user asked for Markdown alongside PNG on the view that Markdown will only become more widely read. The third question — swipe and card-layer interaction detail — stays open by design until there is a real screen to finalise it against.

That let the item split at a real seam. The SPEC half became [nav-left-spine-spec-edit] and was kept; the build remainder stayed in Unprocessed, because four sub-features whose screens do not exist cannot say what changes inside which files. The alternative — keeping the whole thing on a promise to design the rest during the build — was rejected: the start of a build is still the build, and an item in that shape stalls a run. [search-feature] gained the matching cross-reference and is now marked to fold into the spec edit and be deleted rather than built, so the relationship is written on both sides rather than surviving on whichever item someone opens first.

The third was the share-format research. The lookup did not change the answer but did change its grounds. The item had leaned PNG as "most universally readable"; in fact Android's share sheet filters targets by MIME type, so PNG and PDF are equally reachable and compatibility decides nothing. What differs is arrival — a PNG renders inline in a chat thread where a PDF arrives as an attachment to open — which is what favours PNG for a short read-once summary. A follow-up check settled that Markdown must travel as `text/plain`: `text/markdown` is a registered type that almost no Android app declares, so declaring it would produce a near-empty share sheet. Both findings are filed with an index line, and the file states plainly what was not found — no source comparing real-world acceptance across specific apps, and nothing 2026-specific.
