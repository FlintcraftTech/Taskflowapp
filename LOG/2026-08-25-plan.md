**The red flag came first and is now cleared, designed out rather than accepted.** [mcp-server-auth-model] asked how the remote MCP server ties a request to a user. The answer turned on an external fact nobody here could supply from memory — what Anthropic's custom-connector surface accepts today — so the session looked it up before deciding anything, and filed the finding at `resources/research/claude-custom-connector-auth-options.md`. It settled the question harder than expected: a per-user secret in the connector URL is ruled out by Anthropic's own guidance, because a URL carrying a token leaks through server logs, proxy logs, browser history and screenshots; a pasted static key has no consumer-facing field to paste into, since the add-connector flow asks only for a URL; and OAuth with dynamic client registration needs no registration with Anthropic. So the choice was not between two options — it was OAuth or nothing safe. The user was told the cost plainly, that this means building a real authorisation server, and accepted it. The design went into SPEC §Claude integration via remote MCP and into [0020-remote-mcp-server]'s build block, and the capture itself was deleted: building the server and knowing whose data it serves are one piece of work, not two.
